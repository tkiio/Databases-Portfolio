# My recommendation to Yasmin Kaya

For this dataset, I recommend the reporting copy for the dashboard, based on warm medians of 27.296 ms for 3NF and 19.804 ms for the reporting copy without its machine index. I would keep the transactional tables in 3NF so that each machine, part and job fact has one main place to change. The report's machine index is not an automatic improvement: its median was 27.064 ms with the index and 19.804 ms without it, and the saved plans show the access paths. Changing one site touched 1 normalized row but 4,000 report rows, and the report adds 10832.0 KiB including its remaining indexes if both designs are kept. If a reporting copy is used, I would rebuild it from the normalized tables in one transaction every 30 seconds, publish a last-refreshed timestamp and let readers see either the previous complete version or the new one. This targets roughly 30-second freshness, but rebuilding time, scheduling delays and failures can add lag, so the timestamp must make that visible and refresh failures must be reported. If the dashboard needs immediate correctness, I would read 3NF directly or maintain every affected insert, update and delete in the same transaction, rather than relying on a site-only trigger. I would remeasure with the real workload before extending this decision, because this fixed March query and 200,000-row cache-friendly dataset do not establish production performance.
