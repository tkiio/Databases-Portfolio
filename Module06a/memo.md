# Memo to Lea Winter and Yasmin Kaya

I would keep current readings, corrections and small lookups in SQLite and move the reporting history into a Parquet copy for DuckDB. The corrected dashboard fell from 696.5 ms in SQLite to 5.6 ms in DuckDB, and the monthly query fell from 811.9 ms to 4.5 ms. The SQLite file is 112.69 MB, while the refreshed Snappy copy is 2.46 MB and the Zstandard copy is 1.44 MB. I would not move repeated single-row requests: with one transaction in each engine, 1,000 inserts took 0.37 ms in SQLite and 198.41 ms in DuckDB. I would schedule refresh.py --check at 01:30 before the 02:00 report, with the shift lead responsible for checking whether the scheduled job succeeded. The refresh builds a temporary copy, checks it and then replaces the visible Parquet file so readers get a complete file. If the copy is a day old, it may miss new jobs and corrections, so I would show its age, alert on refresh failure and withhold a current-day report until a valid refresh is available. For this workload I would rather show an older report clearly labelled than silently present stale numbers as current, and I would rerun the refresh or use the slower SQLite query when current data is required.

The compression result is a smaller file with similar warm query time; it is not a promise that Zstandard always makes reads faster. The scheduler would capture the refresh exit status and log, while a separate check would alert if the Parquet file's modification time is too old even when the scheduler stops running. The --check option compares row count and SUM(part_price) to one SQLite snapshot, which catches incomplete copies and many wrong-source mistakes, but it cannot prove that every column matches, detect offsetting price errors, or guarantee that the source itself is fresh. New SQLite writes after that snapshot will wait for the next refresh.
