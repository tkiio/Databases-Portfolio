# Reflection 3

My main takeaway from this module is that an index does not automatically make every query faster. The dashboard query still scanned `order_line` after I tested the suggested indexes, but the single-day orders query changed from `SCAN orders` to `SEARCH orders USING INDEX ix_orders_ordered_on`. In my repeated-batch measurement, its median went from 0.978 ms to 0.058 ms. I also learned that wrapping the indexed date column in `date()` made SQLite scan again. I want to remember to check both the plan and the measured time instead of trusting an index suggestion.

The injection drill made the difference between SQL and data clearer to me. A name containing an apostrophe broke the unsafe query, and the payload `' OR '1'='1` made it return rows. Bound parameters treated both inputs as values. I also translated the dashboard query into relational algebra and compared grouped, correlated-subquery, and window-function versions of the late-orders report. The three report versions returned the same 400 customers and counts. The window version was interesting, but it needed extra logic to keep one row per customer.

The hands-on experiments were good because I could see actual `SCAN` and `SEARCH` plan lines and compare them with query results. I struggled at first with entering SQL at the SQLite prompt and once left an unfinished statement open, but cancelling it and starting a clean statement helped me recover. I used ChatGPT as a study helper to interpret the output and check my next steps.
